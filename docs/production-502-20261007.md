# 2026-10-07 生产站点 502 故障记录

生产站点为 `https://isbf-one.com`。本次处理没有发布新代码、重建生产容器、
修改生产配置或恢复数据库备份。CSV 批量邀请码功能仍只在开发工作区。

## 观察到的故障链路

以下时间来自生产日志，统一为 UTC；北京时间加 8 小时。

- 03:35 左右，应用及后台任务出现 Redis 连接和读取超时。
- 03:37，Pitchfork 工作进程及 mold 超时。
- 03:38，mold 被终止，应用 monitor 因没有存活的 mold 退出。
- 03:38–03:39，Nginx 无法连接应用的 `127.0.0.1:3000`，产生 502。
- 03:39，runit 自动重新启动应用；两名网页工作进程与后台任务进程就绪。

容器一直处于运行状态，没有容器重启。检查时生产 cgroup 的 `oom` 和
`oom_kill` 均为 0，不能将日志中的 SIGKILL 直接解释为内存不足杀进程；
日志明确记录了 Pitchfork 超时后主动终止进程。宿主机内核日志无法读取。

## 资源压力与处理

开发和生产共用约 3.5 GiB 内存。检查时约 3.5–3.8 GiB swap 已使用，
内存与 I/O 的 PSI 指标显示明显等待；若干应用进程也处于磁盘等待状态。
同期开发环境正在启动额外的测试网页服务并运行浏览器测试。
这些事实支持资源争用是一个影响因素，但没有故障发生时的完整监控数据，
尚不能证明唯一根因。

已终止本次额外启动的测试服务，保留已有开发数据库和前端构建进程。
生产应用由已有 runit 自动恢复，不需要再次重启。随后多次从 HTTPS 检查
首页与 `/srv/status`，均返回 200，响应时间约 0.03–0.4 秒；Redis 返回
`PONG`，生产 Nginx、应用、PostgreSQL 和 Redis 服务正常运行。
恢复过程中曾观察到一次请求超时及 503，后续检查恢复正常。

在同一台机器上继续运行测试时，使用单独的临时容器，并为测试网页服务与
浏览器共同设置内存上限 1280 MiB、禁止额外 swap、CPU 上限 0.75 核。
只运行本次变更涉及的检查，结束后删除临时容器。该限制针对测试容器，
不改变生产服务的资源配置。

## 后续排查

如再次发生，先查看应用是否自动恢复及 Nginx upstream 错误时间，结合
应用超时日志、`memory.events`、PSI 和磁盘等待判断原因。
避免仅因 Docker 显示容器运行中就判断网站健康；使用 HTTPS 的实际响应确认。
后续开发检查不得在缺少资源上限时同时启动额外 Rails 与浏览器进程。
