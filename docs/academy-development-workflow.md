# 学院论坛开发协作规范

这份文档面向 2–3 人开发团队，作为建立协作流程的建议版本。团队确认后共同执行，并通过 PR 更新规范。

代码的共同版本保存在 GitHub。每位开发者在独立环境中修改，通过 Pull Request（PR，合并申请）让另一人检查，合并后由发布负责人部署指定版本。

## 现在先执行的最小流程

对当前 2–3 人团队，日常先落实以下四条：

1. 每人使用独立代码目录，每个任务从更新后的 `main` 建一个功能分支。
2. 工作结束前提交并推送进展到自己的分支，保存到 GitHub。
3. 完成后开 PR，由另一位同学检查改动和效果，再合并到 `main`。
4. 由指定负责人发布已经合并并验证的版本，不再通过上传整个目录替换服务器代码。

开始执行前，先按下一节保存各处现有成果，尤其是尚未提交的代码和后台主题。

小任务可以先在群里协调负责人和验收要求，最终写进 PR；跨多日或需要多人配合的任务再建 Issue。发布记录可以直接补在 PR 中，记下上线时间、提交编号和结果。规范中的独立测试环境、完整发布记录和更全面的自动化检查逐步完善；涉及权限、数据库或上游升级的发布，仍需要先在隔离环境中验证。

## 1. 先保存现有成果

在第一次按新流程发布前，暂停向生产服务器上传或覆盖代码，完成以下盘点：

1. 保存服务器代码目录的完整副本，包含未跟踪文件；备份数据库、上传文件和部署配置。备份另存到服务器之外，按时间标记。
2. 每位开发者也保存自己的工作目录副本。不要用某个人的整个目录覆盖另一人的目录。
3. 在每个代码目录执行下面的只读命令，记录远端、分支、提交和未提交修改：

   ```bash
   git remote -v
   git branch --show-current
   git rev-parse HEAD
   git status --short
   git diff --stat
   ```

4. 从 Discourse 后台导出正在使用的主题及主题组件，记录主题 ID、设置、关联组件和插件清单。数据库里的主题和仓库里的文件都要保留。
5. 确认生产环境的启动方式、代码来源、数据库与上传目录、重启方式，以及是否由 `discourse_docker` 管理。不要把本地开发目录当成生产部署目录。
6. 把各处尚未入库的功能分别整理到功能分支，通过 PR 比较、合并和验收，形成第一份共同基线。合并前排除密码、私钥、数据库备份等文件。
7. 确认共同基线包含所有要保留的功能，在隔离环境中验收，再开始统一发布。

检查本仓库时，工作区存在未提交修改，`plugins/discourse-academy-roles/` 也尚未被当前检出版本跟踪。盘点时必须纳入这些文件。以上观察不能证明生产服务器的状态。

Discourse 站点备份包含数据库，是否包含上传文件取决于备份选项；插件代码和服务器部署配置需要另外保存。参见 [Discourse 备份说明](https://meta.discourse.org/t/create-download-and-restore-a-backup-of-your-discourse-database/122710)。

## 2. 分支与环境

| 对象 | 用途 | 规则 |
| --- | --- | --- |
| GitHub `main` | 团队已经审查、期望可以发布的代码 | 所有修改通过 PR 合并 |
| `feat/42-calendar` 等功能分支 | 一个任务的开发过程 | 每个任务新建，完成后删除 |
| 个人开发环境 | 写代码、调试、运行测试 | 每人独立代码目录和数据库 |
| 测试环境 | 验收一次发布候选版本 | 可逐步建设；高风险变更先在隔离环境演练 |
| 生产环境 | 学院成员使用的论坛 | 只部署已验收的指定版本 |

先采用一个长期 `main` 分支，加若干短期功能分支。测试环境是一套运行环境，不需要专门建立长期 `develop` 或 `staging` 分支。生产版本可以落后于 `main`，但必须知道它对应哪个提交。

电脑无法运行 Discourse 时，可以使用远程开发环境。即使共用一台开发服务器，也必须有各自的目录、进程、数据库和端口，不能共用一个可写的 Git 工作目录，也不能连接生产数据库调试。

本仓库的两个远端含义：

- `origin`：学院仓库 `ISBF-Lab/ISBFweb`，团队功能提交到这里。
- `upstream`：Discourse 官方仓库，用于计划中的上游升级。

这一分支流程参考 [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)。

## 3. 分工与 GitHub 设置

每个人使用自己的 GitHub 账号和 SSH 密钥。开发者通常拥有仓库 Write 权限；指定一位发布负责人和一位备份负责人，生产环境使用个人身份登录，避免共享账号。

开始任务时写清要解决的问题、负责人和验收条件。例如：“手机上回复按钮可以打开编辑器，并正确回复当前话题”。小任务最终记录在 PR 中，跨多日或需要多人配合的任务建立 GitHub Issue。同一任务主要由一人负责；准备同时改同一组件或样式文件时，先沟通并记录。

仓库管理员在 `Settings → Rules → Rulesets`，或 `Settings → Branches` 的分支保护中保护 `main`：

- 必须通过 PR 合并。
- 至少一位其他开发者批准。
- 代码变更后重新审查，可启用撤销过期批准。
- 审查讨论必须解决。
- 禁止强制推送和删除 `main`。
- 普通流程中管理员也遵守保护规则。
- CI 确认能正常运行后，要求相关检查通过再合并。

先用一个试验 PR 确认现有 Actions 的执行结果和准确检查名称，再设置必需检查。仓库已有上游的 `Tests` 和 `Linting` 工作流，但仍需确认它们能在学院仓库中运行，并覆盖学院自定义插件和主题。

普通功能 PR 推荐 `Squash and merge`，把一个功能归并为一个提交，便于查看和撤销。上游升级 PR 使用保留历史的 merge commit，因此仓库保留这两种合并方式，暂不启用强制线性历史。合并后自动删除功能分支。

规则功能受 GitHub 套餐和仓库可见性影响。公开组织仓库可使用免费套餐的分支保护；私有组织仓库需核实套餐支持。如果当前套餐无法强制保护，就要明确这是人工约定，不能宣称已经有技术拦截。参见 [分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) 和 [Rulesets 可用范围](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)。

## 4. 每次开发的操作

Git 的几个词：`commit` 是把选定改动保存为本地版本；`push` 是把提交发到 GitHub；PR 是请求把功能分支合入 `main`；`merge` 是合并两边的改动。上传目录不能代替这些操作。

首次开发时，在自己的开发机器或独立开发目录中克隆一次：

```bash
git clone git@github.com:ISBF-Lab/ISBFweb.git
cd ISBFweb
git config user.name "你的名字"
git config user.email "你的 GitHub 提交邮箱"
```

账号需要先配置 SSH 认证；邮箱可以使用 GitHub 提供的隐私邮箱。

每个新任务从更新后的 `main` 建分支。下面命令要求当前没有未提交改动；有改动时先在当前功能分支保存，不能直接照抄切换：

```bash
git status
git switch main
git pull --ff-only origin main
git switch -c feat/42-calendar
```

修改并验证后，只暂存本任务的文件。下面用文档文件演示，开发时换成自己实际修改的文件路径：

```bash
git diff
git add docs/academy-development-workflow.md
git diff --cached
git commit -m "DOC: Document academy development workflow"
git push -u origin feat/42-calendar
```

每个工作日结束前，把值得保存的进展提交并推送到自己的功能分支。尚未完成时可以创建 Draft PR；这不会把功能发布到线上。分支已经设置过上游后，后续提交使用 `git push`。

准备审查时，打开 GitHub 仓库创建 PR，目标选择 `main`，写清：

```text
关联任务：Closes #42
修改内容：
验收方法和结果：
界面截图（涉及界面时）：
涉及的插件、主题或设置：
发布步骤和撤销办法（需要时）：
```

提交审查前，按项目要求运行一次 `bin/lint --fix`，传入本次修改的文件；如果 lint 改了文件，把结果也提交。按照修改范围运行相关 `bin/rspec` 或 `bin/qunit` 测试，并实际验证关键功能。PR 中区分“已运行并通过”和“尚未验证”。

另一位开发者检查改动、验收结果和发布说明。作者处理反馈，检查通过并获批准后再合并。一个 PR 尽量只做一项任务；如果任务持续多天，拆成可独立验收的部分。

PR 合并后，下一项任务重新从更新后的 `main` 建分支，不继续使用已经 squash 合并的旧功能分支。

## 5. 同时修改时怎样避免覆盖

例如，甲修改日历，乙修改回复功能，两人分别从 `main` 建分支。甲的 PR 先合并后，乙的 PR 会把自己的修改与新的 `main` 合并。如果同一处代码不能自动合并，Git 会提示冲突，由双方确认最终内容。

这能避免直接上传目录造成的整片覆盖，但仍需要检查两个功能能否一起正常工作。

需要把最新 `main` 合入自己的功能分支时，先提交当前改动，然后执行：

```bash
git fetch origin
git merge origin/main
```

如果出现冲突，先看 `git status`，与另一位开发者逐个确认冲突文件。不要整文件选择“全用我的”或“全用对方的”。解决后暂存对应文件、完成合并提交、重新验证并推送。不知道怎样处理时，可在这次合并仍未完成的情况下用 `git merge --abort` 退出，再一起处理。

新手日常流程不使用 `git push --force`、`git reset --hard` 或 `git clean -fd`。遇到推送拒绝或更新失败时，保留原工作目录，先读提示和检查分支状态。

## 6. 发布与撤销

代码合并到 `main` 后，由发布负责人选择一个具体提交，验收后发布同一个版本。初期的小修改可在独立开发环境完成相关验收；涉及权限、数据库或上游升级时，先在与生产配置相符的隔离环境演练。建立专用测试环境后，在其中验收发布候选版本。合并 PR 和发布线上是两个操作；初期采用人工发布，熟悉后再做自动化。

每次发布按这个顺序进行：

1. 确定候选提交；记录核心、插件、主题分别来自哪里，以及各自的版本或提交。
2. 在独立开发或测试环境验证登录、邀请注册、普通与官方发帖、回复、匿名功能、日历和手机布局中本次相关的路径。
3. 记录当前生产版本和恢复办法，确认备份可用；涉及数据库、权限或上游升级时，准备新备份并先在测试环境演练。
4. 确认生产没有未经保存的本地改动，按核实过的部署步骤安装候选版本。发现生产独有改动时停止覆盖，先保存并纳入 Git。
5. 同步本次发布的主题、插件和必要配置，检查站点与后台任务，记录验收结果。
6. 在 PR、GitHub Release 或发布 Issue 中记录时间、负责人和上线提交。涉及多个组件、设置或备份时，补充相应清单和位置。发布完成前不允许另一个人并行发布。

当前部署方式尚未确认，因此这份规范没有提供可直接执行的生产重建命令。正式启用发布流程前，要补一份实际部署说明，写明代码目录、启动方式、版本固定方式、主题同步方式和恢复步骤。

### 本项目需要特别处理的内容

- `themes/isbf-campus-feed/` 是主题源文件的一份副本，运行中的主题存储在 Discourse 数据库里。Git 拉取或应用重启不会自动同步这两份内容。先导出现有主题，之后以审查后的仓库版本为准，记录每次同步的方法和版本。
- 主题 README 中的 ID 4 描述本地站点，生产主题 ID 需要单独确认。验收时也要确认主题设置和关联组件。
- 本地可以使用主题编辑器试验，但要把最终成果导回功能分支参与审查。生产主题代码由发布步骤更新；后台的内容运营和站点设置调整按职责记录。
- 当前学院仓库包含核心修改。生产构建必须使用学院 fork 的指定版本；只拉取官方 Discourse 再装主题、插件，可能遗漏核心改动。
- 插件的安装和加载方式也要核实。文件出现在 `plugins/` 中不代表生产已加载它。
- `academy_roles:setup` 会重设部分站点设置和分类权限，不能未经确认就放进每次发布流程。

### 核心改动盘点（2026-09-30）

对当前 `feature/isbf-per-post-anonymous` 分支与官方上游的共同基线进行比较，已提交的学院功能位于插件和主题中，没有直接修改核心业务文件。工作区有以下两处尚未提交的核心前端改动：

| 文件 | 改动 | 使用方与作用 |
| --- | --- | --- |
| `frontend/discourse/app/components/generated-invite-link.gjs` | 新增 `generated-invite-link-after-link` 扩展插槽，传入邀请链接 | 学院身份插件在邀请链接下方显示邀请码和复制按钮 |
| `frontend/discourse/app/components/topic-footer-buttons.gjs` | 向已有的 `topic-footer-main-buttons-before-create` 插槽多传入 `inlineButtons` | 学院主题使用原有按钮动作，在桌面端“更多”菜单显示举报和标记未读 |

两处修改提供扩展接口，具体行为仍由插件和主题实现。此次盘点未发现直接修改核心后端、数据库迁移或核心权限文件。

另有仓库配置和依赖变化：已提交版本关闭了 Dependabot 版本更新，`.gitignore` 允许跟踪自定义插件；工作区的 `pnpm-lock.yaml` 移除了部分覆盖版本和补丁配置，并出现 TypeScript 依赖解析变化。锁文件变动的原因需要单独核对，不能作为学院业务改动直接发布。以上是当前工作区记录，不代表生产服务器已运行这些改动。

后续可以把主题接入独立 Git 仓库，再通过 Discourse 的 Git 主题更新机制发布；拆仓库前先明确核心、主题、插件之间的版本配套，避免引入新的同步问题。参见 [Discourse 主题安装方式](https://meta.discourse.org/t/how-do-i-install-a-custom-theme-on-my-discourse-instance/306418)。

### 出问题时

普通代码错误可以通过撤销对应提交的 PR 修复，再发布修复版本。对于没有数据库兼容变化的发布，也可以按经过验证的部署步骤恢复上一个代码版本。

涉及数据库迁移时，旧代码未必能读取新数据库，不能默认“切回旧提交”就能恢复。恢复数据库备份会丢失备份之后的新帖子等数据，应先评估影响并保存当前数据；日常代码撤销不自动恢复数据库。

紧急修复也建立 `fix/` 分支并通过 PR。优先采用已知的停用相关功能或恢复步骤，避免直接在线上写新代码形成未记录的版本。

## 7. Discourse 上游升级

由一位负责人定期安排升级，选定官方版本，不把升级混入日常功能 PR：

1. 从学院 `main` 建立 `chore/update-discourse-版本` 分支。
2. 获取 `upstream` 的选定版本，在该分支合并并处理冲突。
3. 检查学院插件、主题和核心修改的兼容性，测试数据库升级。
4. 创建独立升级 PR，用保留上游提交历史的 merge commit 合并，避免将整个上游升级 squash 成一个提交。
5. 在测试环境验收，备份后按发布流程上线。

学院业务功能优先通过插件和主题扩展；确需修改核心时，在对应 PR 中说明扩展点为什么不足，便于后续升级时审查。

## 8. 落地顺序

先完成以下项目：

- [ ] 共同保存服务器、主题编辑器和各人工作目录中的现有成果。
- [ ] 明确生产部署方式、代码来源和当前版本。
- [ ] 每人建立独立开发环境。
- [ ] 指定发布负责人和备份负责人。
- [ ] 在 GitHub 启用适用的 `main` 保护规则。
- [ ] 用一个小修改走通分支、提交、推送、PR、审查与合并。
- [ ] 写明现有环境的实际部署与恢复步骤，在 PR 中记录首次上线版本。

流程运行后逐步完善：

- [ ] 确认现有 CI 正常运行，并按修改范围补充自定义功能的检查。
- [ ] 建立专用测试环境；高风险发布在此之前也要安排隔离演练。
- [ ] 多个组件开始独立发布时，使用统一的发布清单。

规范、环境搭建方法和发布步骤保存在仓库文档中；任务与审查保存在 Issue/PR 中；版本与发布结果保存在 Release 或发布 Issue 中。密钥、数据库备份和包含密码的真实部署配置存放在访问受控的位置，仓库只保存去掉秘密的示例。
