# PR 验证与 CI 修复流程

状态：已启用插件定向检查、主题失败日志上传和后续系统测试门禁；进一步拆分任务尚待配置。

当前已为学习资源和通知插件增加独立的定向后端检查，见
[插件回归工作流](../../.github/workflows/isbf-plugin-regression.yml)。它与已有主题回归分别报告结果，
并在插件任务结束时上传日志。主题 QUnit 失败时立即上传该步骤日志，
跳过无法使本轮 CI 通过的后续系统测试；成功时仍执行全部原有系统测试。

## 1. 确定范围和源码基线

- 记录目标分支、当前 HEAD、本次 diff 和既有未提交修改，只提交已授权范围。
- 区分修改输入与最终发布源码。涉及发布合并时，将最终发布文件及来源摘要回写到受版本控制的源码中，再作为后续工作的基线。
- PR 准备使用源码和现有发布记录；生产环境操作按单独的发布授权执行。

## 2. 修改前完成根因和影响范围分析

- 收齐可取得的失败日志，按根因归类，列出相关调用点及受影响测试。
- 全局异常中断套件时，将后续用例记为未验证，不能把首个错误当作唯一问题。
- 根据改动检查初始化器参数及调用方式、owner/container 生命周期、重复注册、共享 fixture 是否被模型修改、API 响应结构、测试场景前提及运行依赖。
- 形成简短的“错误—根因—影响范围—验证方式”记录后，成组修复同类问题。

## 3. 推送前做定向验证

- 完成实现后，对变更文件运行一次 `bin/lint --fix`。
- 运行受影响的测试模块和必要的交互用例，确认套件完整结束；修复隔离问题时包含曾触发污染的用例及其后续用例。
- lint 结果只证明静态检查状态；功能测试的通过、失败或未运行情况分别记录。
- 按实时资源预算执行。环境或资源不足时，将定向验证前置到隔离 CI，并明确标记本地未验证的行为。
- 已通过的检查只在新增改动、失败或仍有相关疑点时重跑。

## 4. CI 先提供快速功能反馈

- 将必要的静态检查、定向测试和主题 QUnit 放在耗时系统检查之前，保留原生回归与主题测试各自的环境边界。
- 相关快速检查通过后再运行依赖它们的完整回归；合并仍要求全部必需检查成功。
- 失败步骤立即上传日志和诊断信息，避免等长时间系统检查结束后才能取得错误细节。
- CI 失败后回到根因归类和定向验证步骤，修复同类调用点，更新同一个 PR。
- 通过修复代码或测试前提消除失败，保留原有行为断言；测试数量减少、跳过或单纯增加超时不作为修复证据。

## 5. 按已验证的提交合并

- 确认全部必需检查对应 PR 当前 HEAD，并以该 SHA 执行合并。
- 代码在检查成功后发生变化时，取得新提交所需的检查结果。
- PR 描述保存最终问题、实现、验证范围及实际结果；同步本地 main 时保留其他未提交工作。
